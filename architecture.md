## Content model — where the built site's Markdown actually comes from

**This is the single most important structural difference from stock Quartz v4 to keep
in mind during migration**: the build's content root is NOT `content/`. It is the
`dsview_vault` git submodule, selected at build time via the CLI flag:

```
npx quartz build -d dsview_vault
```

(`-d` = `argv.directory` in `quartz/build.ts`, i.e. Quartz's content-directory flag).
The `content/` folder in this repo is vestigial (`content/.gitkeep` only). Any v5
migration must confirm the equivalent CLI flag/behavior exists and keep pointing it at
`dsview_vault/`, and must keep the CI submodule-pull step
(`git submodule update --remote --recursive`) so the build always uses the latest
content commit rather than whatever SHA is pinned in `.gitmodules`.

The vault content itself follows a folder convention that `graph.inline.ts` depends on
via `filePath` prefix matching (see `spec.md` §2):

```
dsview_vault/
├── contents/   → "content" items (papers, courses, posts, repos...) → red graph nodes
├── Concept/    → ML/DS concept topic pages           → purple nodes
├── Dataset/    → dataset topic pages                 → dark purple nodes
├── Library/    → library topic pages                 → gold nodes
├── Model/      → model topic pages                   → cyan nodes
├── Platform/   → platform topic pages                → blue nodes
└── Tool/       → tool topic pages                     → teal nodes
```

## Suggested migration approach

1. Add Quartz v5 as a new remote/branch (or fetch its tag) and diff it against the
   `7a77f54` fork point to see what upstream itself changed in each of the files listed
   above — that tells you which changes are pure additions (safe to reapply verbatim)
   vs. which touch code v5 restructured (need manual re-porting).
2. `quartz/components/scripts/graph.inline.ts` and
   `quartz/components/pages/FolderContent.tsx` are the highest-risk files: both rely on
   internal data shapes (`filePath` on `QuartzPluginData`, `folder.entries()` on the file
   tree) that a major version bump is most likely to have changed. Verify these APIs
   still exist with the same contract before reapplying the diffs.
3. `quartz.config.ts`, `quartz.layout.ts`, `quartz/util/theme.ts`,
   `quartz/styles/variables.scss`, `quartz/components/styles/graph.scss` are
   low-risk, additive config/styling changes — should port with at most minor
   type-shape adjustments.
4. The CI workflow and submodule wiring are independent of the Quartz version and can
   be carried over unchanged, aside from re-checking that `-d <dir>` (or its v5
   equivalent) still designates the content root.
